A Glimpse of What Enterprise RAG Can Look Like

August 15, 2026

Overview

In this project I built a hybrid RAG system on top of aerospace manufacturing data, using semi-structured documents and a full retrieval evaluation suite. The goal is to give you an inside look at how a RAG pipeline is actually constructed — the tooling, the search and ranking mechanisms, and why this kind of system is genuinely useful for an organization that sits on a corpus of domain-specific documents.

The steps I took, in order, were:

  • Generating synthetic data using Llama 3.3 70B Instruct
  • Creating token-aware chunks
  • Embedding chunks with Cohere's Embed v3 model
  • Storing vectors in a ChromaDB vector database
  • Dense retrieval using cosine similarity
  • Sparse retrieval using BM25Okapi
  • Applying Reciprocal Rank Fusion (RRF), merging the dense and sparse retrieval
  • Reranking and rescoring with Cohere's Rerank v4
  • Generating responses to a query using Claude Sonnet via OpenRouter
  • Evaluation harness using Hit Rate, MRR, and NDCG@5

Here is a high-level diagram of the pipeline with an explanation of each step in the process.

Generating Synthetic Data

Manufacturing datasets are sparse online — they are typically company proprietary, export-controlled, and contain sensitive information. The solution for this project was to use an open-weight LLM to synthetically craft 500 documents that follow authentic aerospace quality management patterns.

Document types generated

Type Count What it represents
NCR (Non-Conformance Report) 150 A part that failed inspection — records the defect, part number, supplier, disposition
ECR (Engineering Change Request) 100 A formal request to change a drawing or specification
Supplier Audit 100 A quality audit of a supplier's manufacturing process
Corrective Action Report 100 Root cause analysis + action plan for a recurring defect
Incident Report 50 Safety or process incident during manufacturing

How the generator works

The script builds a context dictionary for each document (random part numbers, suppliers, defect types from curated vocabulary lists), converts it into a detailed prompt, sends it to Llama 70B, and writes the result as JSONL. 

# Domain vocabulary — grounds the LLM in realistic aerospace language
SUPPLIERS = [
    "Apex Precision Components", "Orbital Fasteners Ltd",
    "NovaTech Composites", "Sterling Hydraulics", ...
]

DEFECT_TYPES = [
    "Dimensional out-of-tolerance",
    "Porosity detected on X-ray",
    "Coating adhesion failure", ...
]

The sampling parameters used

Parameter Value Effect
temperature 0.8 Controls how random and/or creative the text will be. 0 = deterministic. 1.0 = very random. A value of 0.8 allowed varied narratives while staying coherent.
top_p 0.92 (nucleus sampling) Controls how many word choices the model has. Higher = more variety and creativity. More variety resembles enterprise data more closely.
frequency_penalty 0.4 Lowers the chance of a word being repeated. Ranges from -2.0 to 2.0. At 0.4, words can repeat a few times before being penalized.
max_tokens 800 Cap on output length. 800 tokens is roughly 600 words — enough for a complete narrative without runaway generation.

Output format — JSONL

The output is in JSONL format and an example is shown here. JSON is considered semi-structured data. Aerospace (and manufacturing) data comes in structured, semi-structured, and unstructured forms. For the first iteration of this project I stuck with semi-structured data. In future iterations I will be exploring RAG systems with all structures of text data along with multimodal data.

Chunking

Before we can embed a document, it must be split into chunks. Embedding models have a context window (typically 512 tokens long), so documents that exceed this length cannot be embedded as a single unit without the model truncating them or erroring out.

I went with sentence boundary chunking — creating chunks on sentence boundaries and only starting a new chunk when adding a new sentence to the current chunk would exceed 512 tokens. Tokens were counted using tiktoken's cl100k_base model.

Visual walkthrough of the chunking overlap

When chunking, a query could reference something that spans two chunks. For example, an NCR could mention details that exceed a chunk boundary and land in the next chunk. To handle this, chunks include a 64-token overlap. This is visualized below.

Embedding Chunks with Cohere Embed v3

Once documents are chunked, the next step is converting each chunk into a vector — a fixed-length list of floating point numbers that represents the semantic meaning of the text. This is what allows us to search by meaning rather than just keywords. Similar chunks produce vectors that are close together in a high-dimensional space, even if they share no exact words.

For this project I used Cohere's Embed v3 model (embed-english-v3.0).

The input_type distinction

An important caveat about Cohere's embedding API is that it requires you to declare whether you are embedding a document (being stored in the index) or a query (being searched at runtime). The model uses different internal encoding paths for each. Using the wrong type silently degrades retrieval quality — you get plausible-looking but sub-optimal results with no error message. 

# At index time — encoding chunks for storage
embed_documents(texts)  # input_type = "search_document"

# At query time — encoding the user's question
embed_query(text)       # input_type = "search_query"

Batching and error handling

The embedder processes chunks in batches of 96 texts per request. For our 398 chunks that means 5 API calls per index build. To handle API errors gracefully, the embedder includes a retry loop that catches any TooManyRequestsError and waits 61 seconds before retrying the same batch — useful when running multiple index builds in the same session. 

except TooManyRequestsError:
    print(f"Rate limit hit — waiting 61s ...")
    time.sleep(61)

The output of this step is a float32 vector for each chunk, ready to be stored in ChromaDB.

Storing Vectors in ChromaDB

ChromaDB is an open-source vector database. It stores triples (vector, document, metadata) and supports quick approximate nearest-neighbour search. The vectors are stored on disk and persist between sessions, so you only need to embed your documents once.

For this project the vectors are stored in a named collection (mfg_rag_cohere_v3) within ChromaDB's persistent directory on disk.

Why cosine similarity?

ChromaDB supports multiple distance metrics. I chose cosine similarity because it measures the angle between two vectors rather than their magnitude. This means two chunks about the same topic will score highly regardless of their length. Euclidean distance penalizes shorter chunks because their vectors have smaller magnitudes — cosine is invariant to this and is the standard choice for embedding-based retrieval.

ChromaDB returns cosine distance (0 = identical, 2 = opposite). We convert it to similarity with a simple inversion: score = 1 - distance, so that higher always means more relevant, consistent with BM25 scores in the next step.

Dense Retrieval

With the index built, we can retrieve relevant chunks for any query. Dense retrieval works by embedding the user's query using the same Cohere model (with input_type = "search_query") and asking ChromaDB to find the 20 most similar vectors using the HNSW index. HNSW (Hierarchical Navigable Small World) is a graph-based approximate nearest-neighbour algorithm — it finds the most similar vectors quickly without comparing the query against every chunk in the database, which would be far too slow at scale.

This is where the power of embeddings shows up. A query like "which parts had internal voids?" will retrieve chunks about porosity defects even though the word "porosity" never appears in the query — because both concepts map to nearby regions of the vector space.

We retrieve the top 20 candidates at this stage rather than the final 5, because the reranker at the end of the pipeline is much better at precise ranking. The retriever's job is to cast a wide enough net that the right documents are in the candidate pool.

Sparse Retrieval using BM25Okapi

Dense retrieval alone has a blind spot: exact keyword matching. A query for a specific document ID like NCR-2025-08324 or a rare part number may not produce a meaningful embedding signal — the model simply hasn't seen enough context to know that this string is important. This is where sparse retrieval steps in.

BM25 (Best Match 25) is a classical probabilistic ranking function that scores documents based on term frequency, inverse document frequency, and document length normalization. It requires no embedding model — it operates directly on tokenized text.

score(d, q) = ∑ IDF(qᵢ) · TF(qᵢ, d) · length normalisation IDF — rare terms score higher than common ones TF — how often the query term appears in the document len — prevents long documents from winning just because they contain more words

The BM25 index is built in memory at startup from all chunk texts. At query time, the query is tokenized, scored against every chunk, and the top 20 non-zero results are returned. This takes milliseconds for our dataset size.

The result is two ranked lists — one from dense retrieval, one from sparse — which we now need to merge.

Reciprocal Rank Fusion (RRF)

We now have two ranked lists of 20 candidates each, and they may overlap partially. The question is: how do we merge them into a single ranked list in a principled way?

The answer is Reciprocal Rank Fusion, from Cormack, Clarke & Buettcher (SIGIR 2009). The formula is:

RRF_score(d) = ∑ 1 / (k + rank(d)) lists Where k = 60 (the constant from the original paper) and rank is 1-based. A document at rank 1 in the dense list contributes 1/(60+1) ≈ 0.0164. A document appearing in both lists accumulates score from each.

The constant k = 60 controls how aggressively top ranks are rewarded. It was empirically shown to generalize well across retrieval tasks without dataset-specific tuning, which is why it has become the standard default.

The output of RRF is a single merged list. We pass the top 20 fused candidates to the reranker.

Reranking with Cohere Rerank v4

The retrievers so far — both dense and sparse — are bi-encoders. They encode the query and each document independently and find nearby vectors. This is fast but coarse: the query and document never interact during encoding, so subtle relevance signals can be missed.

A cross-encoder reads the query and one document together in a single forward pass, with full attention across both. This is far more accurate but also far too slow to run on the full corpus. The solution is to use it only on the shortlist: the top 20 fused candidates from RRF.

Cohere Rerank v4 (rerank-v4.0-fast) re-scores each of the 20 candidates against the query and returns the top 5 with a rerank_score between 0 and 1. In practice, the reranker frequently promotes documents that the bi-encoder ranked 8th or 10th to the top 3 — particularly for queries with nuanced intent that dense similarity alone misses.

The top 5 reranked chunks become the context for the generation step.

Generating Responses with Claude Sonnet

The final retrieval step hands off to Claude Sonnet (via OpenRouter) to generate a grounded natural language answer from the top 5 chunks. The key design constraint is that Claude is explicitly instructed to answer only from the provided context — no external knowledge, no hallucination. If the answer is not in the chunks, it says so. 

_SYSTEM_PROMPT = """
You are a quality engineering assistant for an aerospace manufacturing company.
Answer the user's question using ONLY the information in the provided context documents.
If the answer cannot be found in the context, say so clearly — do not guess.
When referencing specific information, cite the document ID (e.g. "per NCR-2024-00042").
"""

Each chunk is numbered and labeled with its doc ID, type, and supplier before being passed to the model. This makes citation straightforward and keeps the answer traceable back to the source document — which is what makes RAG trustworthy in an enterprise context.

Why OpenRouter?

OpenRouter is an API gateway that provides access to models from many providers under a single API key. This project already used an OpenRouter key for the Llama 70B synthetic generation step, so reusing it for Claude avoided adding a second API key and separate billing account.

Evaluation Harness

A pipeline that "works" is not the same as a pipeline that is measurably good. The evaluation harness provides the numbers.

The golden dataset

I built a golden dataset of 27 queries by deriving them directly from the structured metadata fields that Llama 70B used when generating each document. Because the metadata records defect_type: "Porosity detected on X-ray" for each NCR, we can automatically generate the query "Which NCRs involved porosity defects?" and know with certainty which doc IDs are the correct answers — no manual labeling required.

This approach gives deterministic, verifiable ground truth across all 5 document types.

Metrics

Three standard retrieval metrics were computed at k=5 (top 5 results):

Hit Rate@5 0.89

At least one correct document appeared in the top 5 (24/27 queries)

MRR@5 0.74

Average reciprocal rank of the first correct document (1/rank, averaged)

NDCG@5 0.62

How well all correct documents were ranked across the top 5 (logarithmically discounted)

An MRR of 0.74 means that on average the first relevant document lands around rank 1–2, which is strong for a 27-query benchmark on a domain-specific corpus. The 3 misses (ncr_defect_material_cert, ncr_disposition_uai, ncr_severity_critical) are queries where the pipeline's top 5 contained no ground-truth relevant documents — areas to improve in future iterations.
